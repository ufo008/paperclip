# Paperclip 规格说明

Paperclip 控制平面的目标规格说明。活文档——在规格访谈期间逐步更新。

---

## 1. 公司模型 [草案]

Company（公司）是一阶对象。一个 Paperclip 实例运行多个 Company。Company 没有独立的"目标"字段——其方向由其 Initiative（战略计划）集合定义（参见任务层级映射）。

### 字段（草案）

| 字段          | 类型          | 备注                             |
| ------------ | ------------- | --------------------------------- |
| `id`        | uuid          | 主键                           |
| `name`      | string        | 公司名称                        |
| `createdAt` | timestamp     |                                   |
| `updatedAt` | timestamp     |                                   |

### 董事会治理 [草案]

每个 Company 都有一个**董事会（Board）**来治理高影响力决策。董事会是人类监督层。

**V1：单一人类董事会。** 一位人类操作员。

#### 董事会审批门控（V1）

- 新 Agent 聘用（创建新 Agent）
- CEO 的初始战略分解（CEO 提出，董事会在执行开始前审批）
- [待定：其他需要治理审批的操作——目标变更、解雇 Agent？]

#### 董事会权限（始终可用）

董事会拥有**不受限制的**系统访问权限：

- **设置和修改公司预算**——董事会设置顶层 token/LLM 成本预算
- **暂停/恢复任何 Agent**——立即停止 Agent 的心跳
- **暂停/恢复任何工作项**——暂停任务、项目、子任务树、里程碑。暂停的项目不会被 Agent 拾取。
- **完整的项目管理访问权限**——通过 UI 创建、编辑、评论、修改、删除、重新分配任何任务/项目/里程碑
- **覆盖任何 Agent 决策**——重新分配任务、更改优先级、修改描述
- **随时手动更改任何预算**

董事会不仅仅是审批门控——它是一个实时控制面。人类可以随时在任何层面进行干预。

#### 预算授权

董事会设置公司级预算。CEO 可以为其下的 Agent 设置预算，每个 Manager Agent 都可以为其下属做同样的设置。这种级联预算授权在实践中如何运作尚待确定，但权限结构支持它。董事会可以随时手动覆盖任何层级的预算。

**未来治理模式**（非 V1）：

- 聘用预算（每月在 $X 以内自动批准聘用）
- 多成员董事会
- 授权权限（CEO 在限额内可以聘用）

### 待解决问题

- 外部收入/支出跟踪——未来的插件。Token/LLM 成本预算是核心功能。
- 公司级设置和配置？
- 公司生命周期（暂停、归档、删除）？
- 除了聘用和 CEO 战略审批外，还存在哪些需要治理审批的操作？

## 2. Agent 模型 [草案]

每个员工都是一个 Agent。Agent 是劳动力。

### Agent 身份（Adapter 级）

像 SOUL.md（身份/使命）和 HEARTBEAT.md（循环定义）这样的概念**不是 Paperclip 协议的一部分**。它们是特定于 adapter 的配置。例如，OpenClaw adapter 可能使用 SOUL.md 和 HEARTBEAT.md 文件。Claude Code adapter 可能使用 CLAUDE.md。一个裸 Python 脚本可能使用命令行参数。

Paperclip 不规定 Agent 如何定义其身份或行为。它提供控制平面；adapter 定义 Agent 的内部工作原理。

### Agent 配置 [草案]

每个 Agent 都有一个**adapter 类型**和一个**特定于 adapter 的配置 blob**。adapter 定义存在哪些配置字段。

#### Paperclip 协议（Paperclip 知道的内容）

在协议级别，Paperclip 跟踪：

- Agent 身份（id、name、role、title）
- 组织位置（他们向谁汇报，谁向他们汇报）
- Adapter 类型 + adapter 配置
- 状态（active、paused、terminated）
- 成本跟踪数据（如果 agent 报告了的话）

#### Adapter 配置（Agent 特定）

每种 adapter 类型定义自己的配置模式。例如：

- **OpenClaw adapter**：SOUL.md 内容、HEARTBEAT.md 内容、OpenClaw 特定设置
- **Process adapter**：要运行的命令、环境变量、工作目录
- **HTTP adapter**：端点 URL、认证头、payload 模板

#### 可导出的组织配置

一个关键目标：**整个组织的 agent 配置都是可导出的。** 您可以导出一个公司的完整 agent 设置——每个 agent、他们的 adapter 配置、组织结构——作为一个可移植的产物。这支持：

- 共享公司模板（"这是一个预建的市场营销代理公司组织"）
- 对公司配置进行版本控制
- 复制/分支公司

#### 上下文传递

可按 agent 配置。频谱的两端：

- **胖 payload**——Paperclip 将相关上下文（当前任务、消息、公司状态、指标）捆绑到心跳调用中。适用于无法回调 Paperclip 的简单/无状态 agent。
- **瘦 ping**——心跳只是一个唤醒信号。Agent 调用 Paperclip 的 API 来获取所需的任何上下文。适用于管理自己状态的复杂 agent。

#### 最小契约

成为 Paperclip agent 的最低要求：**可调用。** 仅此而已。Paperclip 可以通过命令或 webhook 调用您。不要求必须回报——Paperclip 在可能的情况下从进程存活状态推断基本状态。

#### 集成级别

除了最低要求外，Paperclip 提供逐步更丰富的集成：

1. **可调用**（最低）——Paperclip 可以启动您。这是唯一的契约。
2. **状态报告**——Agent 在执行后报告成功/失败/进行中。
3. **完全检测**——Agent 报告状态、成本/token 使用、任务更新和日志。与控制平面的双向集成。

Paperclip 自带**默认 agent**，展示完整集成：进度跟踪、成本检测和用于任务管理的 **Paperclip skill**（用于与 Paperclip API 交互的 Claude Code skill）。这些既是有用的默认值，也是 adapter 作者的参考实现。

#### 导出格式

两种导出模式：

1. **模板导出**（默认）——仅结构：agent 定义、组织图、adapter 配置、角色描述。可选择包含一些初始任务以帮助开始。这是启动新公司的蓝图。
2. **快照导出**——完整状态：结构 + 当前任务、进度、agent 状态。您可以恢复或分支的完整画面。

通常工作流程：导出模板，从中创建新公司，添加几个初始任务，开始。

## 3. 组织结构 [草案]

层级汇报结构。CEO 在顶层，汇报关系向下级联。

### Agent 可见性

**整个组织的完全可见性。** 每个 agent 都可以看到整个组织图、所有任务、所有 agent。组织结构定义**汇报和授权线**，而不是访问控制。

每个 agent 发布其职责和能力简介——几乎像技能描述（"当我有相关任务时"）。这让其他 agent 能够发现谁能帮助完成什么。

### 跨团队工作

Agent 可以在其汇报线之外创建任务并分配给其他 agent。这是跨团队协作的机制。这些规则主要编码在推荐给所有 agent 的 Paperclip SKILL.md 中。Paperclip 应用强制执行工具和一些轻度治理，但下面的跨团队规则主要由 agent 决策实现。

#### 任务接受规则

当 agent 从其团队外部收到任务时：

1. **认为适当且能做** → 直接完成
2. **认为适当但不能做** → 标记为受阻
3. **质疑是否值得做** → **不能自己取消。** 必须重新分配给他们自己的经理，解释情况。经理决定是接受、重新分配还是升级。

#### 经理升级协议

理解为什么下属受阻并解决它是任何经理的责任：

0. **决定**——作为经理，这项工作值得做吗？
1. **向下授权**——请他们下属的人帮助解除阻碍
2. **向上升级**——请他们的上级经理帮助

#### 请求深度跟踪

当任务来自跨团队请求时，将**深度**跟踪为整数——距原始请求者多少个授权跳转。这提供了工作如何通过组织级联的可见性。

#### 计费代码

任务带有**计费代码**，以便在执行过程中可以向上游归因于请求任务/agent 的 token 消费。当 Agent A 请 Agent B 执行工作时，B 的成本被跟踪到 A 的请求。这支持整个组织的成本归因。

### 待解决问题

- 这是严格的树结构还是 agent 可以向多个经理汇报？
- 组织结构可以在运行时变更吗？（agent 重新分配、团队重组）
- Agent 是否从其经理继承任何配置？
- 计费代码格式——简单字符串？层级结构？

## 4. 心跳系统 [草案]

心跳是一种协议，而不是运行时。Paperclip 定义如何启动 agent 的循环。agent 用该循环做什么——运行多长时间、是任务作用域还是连续的——完全取决于 agent。

### 执行适配器

Agent 配置包含一个**adapter**，定义 Paperclip 如何调用 agent。内置 adapter 包括：

| Adapter | 机制 | 示例 |
| ---------------- | -------------------------- | -------------------------------------------------- |
| `process` | 执行子进程 | `python run_agent.py --agent-id {id}` |
| `http` | 发送 HTTP 请求 | `POST https://openclaw.example.com/hook/{id}` |
| `claude_local` | 本地 Claude Code 进程 | Claude Code 心跳工作器 |
| `codex_local` | 本地 Codex 进程 | Codex CLI 心跳工作器 |
| `opencode_local` | 本地 OpenCode 进程 | OpenCode 心跳工作器 |
| `pi_local` | 本地 Pi 进程 | Pi CLI 心跳工作器 |
| `cursor` | Cursor API/CLI 桥接 | Cursor 集成的心跳工作器 |
| `openclaw_gateway` | OpenClaw 网关 API | 通过网关管理的 OpenClaw agent |
| `hermes_local` | 本地 Hermes 进程 | Hermes agent 心跳工作器 |

`process` 和 `http` adapter 作为通用默认值提供。额外的内置 adapter 涵盖常见的本地编码运行时（见上表），新 adapter 类型可以通过插件系统注册（参见插件/扩展架构）。

### Adapter 接口

每个 adapter 实现三个方法：

```
invoke(agentConfig, context?) → void     // 启动 agent 的循环
status(agentConfig) → AgentStatus        // 它在运行吗？完成了？出错了？
cancel(agentConfig) → void               // 优雅停止信号（用于暂停/恢复）
```

这是完整的 adapter 契约。`invoke` 启动 agent，`status` 让 Paperclip 检查它，`cancel` 启用董事会的暂停功能。其他一切（成本报告、任务更新）都是可选的，通过 Paperclip REST API 流转。

### Paperclip 控制什么

- **何时**触发心跳（每个 agent 的调度/频率）
- **如何**触发它（adapter 选择 + 配置）
- **包含什么**上下文（瘦 ping vs 胖 payload，每个 agent 独立）

### Paperclip 不控制什么

- Agent 运行多长时间
- Agent 在其循环期间做什么
- Agent 是任务作用域、时间窗口还是连续的

### 暂停行为

当董事会（或系统）暂停 agent 时：

1. **向当前执行发送信号**——向正在运行的进程/会话发送优雅终止信号
2. **宽限期**——给 agent 时间收拾残局、保存状态、报告最终状态
3. **超时后强制终止**——如果 agent 在宽限期内没有停止，则终止
4. **停止未来心跳**——在新心跳循环被触发前，不会再触发新的心跳周期

这是"优雅信号 + 停止未来心跳"。当前运行有机会正常结束。

### 待解决问题

- 心跳频率——谁控制？固定？按 agent？类 cron？
- 心跳调用失败时会发生什么？（进程崩溃、HTTP 500）
- 健康监控——Paperclip 如何区分"卡住"和"正在处理长时间任务"？
- Agent 能否自我触发下一次心跳？（"我完成了，5 分钟后再唤醒我"）
- 宽限期持续时间——固定？按 agent 可配置？

## 5. Agent 间通信 [草案]

所有 agent 通信都通过**任务系统**流转。

### 模型：任务 + 评论

- **委托** = 创建任务并将其分配给另一个 agent
- **协调** = 在任务上评论
- **状态更新** = 更新任务状态和字段

没有独立的 messaging 或聊天系统。任务是沟通渠道。这将所有上下文附加到与其相关的工作上，并创建自然的审计跟踪。

### 含义

- Agent 的"收件箱"是：分配给他们的任务 + 涉及任务的评论
- CEO 通过创建分配给 CTO 的任务来委托
- CTO 将这些分解为分配给工程师的子任务
- 讨论发生在任务评论中，而不是侧渠道
- 如果 agent 需要升级，他们在父任务上评论或重新分配

### 任务层级映射

完整层级：**Initiative**（公司目标）→ Projects（项目）→ Milestones（里程碑）→ Issues（问题）→ Sub-issues（子问题）。一切都可以追溯到一个 initiative，"公司目标"只是第一个/主要 initiative。

## 6. 成本跟踪 [草案]

Token/LLM 成本预算是 Paperclip 的核心部分。外部收入和支出跟踪是未来的插件。

### 成本报告

完全检测的 Agent 向 Paperclip 报告 token/API 使用情况。成本在每个级别跟踪：

- **每个 Agent**——这个员工花费了多少？
- **每个任务**——这个工作单元花费了多少？
- **每个项目**——这个可交付成果花费了多少？
- **每个公司**——总消耗率

成本应以**token 和美元**双重计价。

任务上的计费代码（参见组织结构）支持跨团队成本归因——当 Agent A 向 Agent B 请求工作时，B 的成本汇总到 A 的请求。

### 预算控制

三个层级：

1. **可见性**——在每个级别显示支出的仪表板（Agent、任务、项目、公司）
2. **软警报**——可配置阈值（例如，在预算的 80% 时警告）
3. **硬上限**——预算用完时自动暂停 Agent。通知董事会。董事会可以覆盖/提高限额。

预算可以设置为**无限**（无上限）。

### 待解决问题

- 成本报告 API——agent 报告成本的模式是什么？
- 仪表板设计——在每个级别哪些指标最重要？
- 预算周期——按天？按周？按月？滚动？

## 7. 默认 Agent 和引导流程 [草案]

### 引导序列

公司如何从"创建"到"运行"：

1. 人类创建公司及其初始 Initiative
2. 人类定义初始顶层任务
3. 人类创建 CEO Agent（使用默认 CEO 模板或自定义）
4. CEO 的第一次心跳：审查 Initiative 和任务，提出战略分解（组织结构、子任务、招聘计划）
5. **董事会审批** CEO 的战略计划
6. CEO 开始执行——创建任务、提出招聘（董事会批准）、授权

### 默认 Agent

Paperclip 自带默认 Agent 模板：

- **默认 Agent**——一个基本的 Claude Code 或 Codex 循环。了解 **Paperclip Skill**（SKILL.md），因此可以与任务系统交互、读取公司上下文、报告状态。
- **默认 CEO**——扩展默认 Agent，包含 CEO 特定行为：战略规划、向下属授权、进度审查、董事会沟通。

这些是起点。用户可以完全自定义或替换它们。

### 默认 Agent 行为

默认 agent 的循环是**配置驱动的**。adapter 配置包含定义 agent 在每次心跳循环中做什么的指令。没有硬编码的标准循环——每个 agent 的配置决定其行为。

这意味着默认 CEO 配置告诉 CEO 审查策略、检查下属情况等。默认工程师配置告诉工程师检查分配的任务、选择最高优先级并处理。但这些是配置选择，不是协议要求。

### Paperclip Skill（SKILL.md）

教 agent 如何与 Paperclip 交互的技能定义。提供：

- 任务 CRUD（创建、读取、更新、完成任务）
- 状态报告（签到、报告进度）
- 公司上下文（读取目标、组织图、当前状态）
- 成本报告（记录 token/API 使用）
- Agent 间通信规则

此技能是 adapter 无关的——可以加载到 Claude Code、注入到 prompts 中，或用作自定义 agent 的 API 文档。

## 8. 架构与部署 [草案]

### 部署模型

**单租户、可自托管。** 不是 SaaS。一个实例 = 一个运营商的公司。

#### 开发路径（渐进式部署）

1. **本地开发**——一条命令安装和运行。嵌入式 Postgres。一切都在您的机器上。Agent 在本地运行。
2. **托管部署**——部署到 Vercel/Supabase/AWS/任何地方。远程 agent 连接到您的服务器，共享数据库。UI 可通过网络访问。
3. **开放公司**——可选择将部分公开（例如，对公众可见的招聘公告板）。

关键约束：从"我在机器上试用"到"我的 agent 在连接到我的 Paperclip 实例的远程服务器上运行"必须非常简单。

#### Agent 认证

当用户创建 Agent 时，Paperclip 生成一个**连接字符串**，包含：服务器 URL、API 密钥和如何认证的说明。假设 Agent 能够弄清楚如何使用其 token/密钥从那里调用 API。

流程：

1. 人类在 UI 中创建 Agent
2. Paperclip 生成连接字符串（URL + 密钥 + 说明）
3. 人类将此字符串提供给 Agent（例如，在其 adapter 配置、环境等中）
4. Agent 使用密钥向控制平面进行 API 调用认证

### 技术栈

| 层级    | 技术                                                   |
| -------- | ------------------------------------------------------------ |
| 前端 | React + Vite                                                 |
| 后端  | TypeScript + Express（REST API，不是 tRPC——需要非 TS 客户端） |
| 数据库 | PostgreSQL（详情参见 [doc/DATABASE.md](./doc/DATABASE.md)——开发用嵌入式 PGlite，生产用 Docker 或托管 Supabase） |
| 认证     | [Better Auth](https://www.better-auth.com/)                  |

### 并发模型：原子任务检出

任务使用**单一分配**（每个任务一个 agent）和**原子检出**：

1. Agent 尝试将任务设置为 `in_progress`（声明它）
2. API/数据库原子地强制执行此操作——如果另一个 agent 已经声明了，请求失败并返回错误，指出哪个 agent 拥有它
3. 如果任务已经从前一个会话分配给请求的 agent，他们可以恢复

不需要乐观锁定或 CRDT。单一分配模型 + 原子检出在设计层面防止冲突。

### 人在循环中

Agent 可以创建分配给人类的任务。董事会成员（或任何有访问权限的人类）可以通过 UI 完成这些任务。

当人类完成任务时，如果请求的 agent 的 adapter 支持 **pingbacks**（例如 OpenClaw hooks），Paperclip 会发送通知来唤醒该 agent。这使得人类成为罕见但可能的 workflow 参与者。

在 Paperclip SKILL 中不鼓励 agent 将任务分配给人类，但有时这是不可避免的。

### API 设计

**单一统一 REST API。** 相同的 API 同时为前端 UI 和 agent 服务。认证决定权限——董事会认证具有完全访问权限，agent API 密钥具有作用域访问权限（他们自己的任务、成本报告、公司上下文）。

没有单独的"agent API"与"board API"。相同的端点，不同的授权级别。

### 工作产物

Paperclip 管理链接到任务的工作产物：附加到问题的文档（附加到问题的富文本计划、规格说明、笔记）和文件附件。Agent 作为正常任务执行的一部分通过 API 读取和写入这些。完整交付基础设施（代码仓库、部署、生产运行时）仍然是 agent 的领域——Paperclip 编排工作，而不是构建管道。

### 待解决问题

- UI 实时更新——WebSocket？SSE？轮询？
- Agent API 密钥作用域——Agent 实际上可以访问什么？仅他们自己的任务？他们的团队？整个公司？

### 崩溃恢复：手动，而非自动

当 agent 在任务中途崩溃或消失时，Paperclip **不会**自动重新分配或自动释放任务。相反：

- Paperclip 通过仪表板和报告显示过时任务（处于 `in_progress` 但没有近期活动的任务）
- Paperclip 不会静默失败——审计和可见性工具使问题显而易见
- 恢复由人类或 emergent 流程处理（例如，一个项目经理 agent 的工作是监控过时工作并将其浮出水面）

**原则：Paperclip 报告问题，而不是静默修复它们。** 自动恢复会隐藏失败。良好的可见性让正确的实体（人类或 agent）决定怎么做。

### 插件/扩展架构

核心 Paperclip 系统必须是可扩展的。知识库、外部收入跟踪和新的 Agent Adapter 等功能应该能够作为**插件**添加，而无需修改核心。这意味着：

- 定义清晰的 API 边界，插件可以挂钩
- 事件系统或钩子，用于响应任务/Agent 生命周期事件
- **Agent Adapter 插件**——新的 Adapter 类型可以通过插件系统注册
- 可注册插件的 UI 组件（未来）

插件框架已发布。插件可以注册新的 adapter 类型、挂钩到生命周期事件，并贡献 UI 组件（例如全局工具栏按钮）。插件 SDK 和 CLI 命令（`paperclipai plugin`）可用于编写和安装插件。

## 9. 前端/UI [草案]

### 主要视图

每个都是一个独立的页面/路由：

1. **组织图**——带有每个 agent 实时状态指示器（运行/空闲/暂停/错误）的组织树。agent 正在做什么的实时活动流。
2. **任务看板**——任务管理。看板和列表视图。按团队、agent、项目、状态筛选。
3. **仪表板**——高级指标：agent 数量、活跃任务、成本、目标进度、消耗率。来自 GOAL.md 的"一瞥"视图。
4. **Agent 详情**——深入了解单个 agent：他们的任务、活动、成本、配置、状态历史。
5. **项目/Initiative 视图**——按里程碑和目标跟踪进度。
6. **成本仪表板**——每个级别（agent、任务、项目、公司）的支出可视化。

### 董事会控制（无处不在）

- 暂停/恢复 agent（任何视图）
- 暂停/恢复任务/项目（任何视图）
- 批准/拒绝待处理操作（招聘、战略提案）
- 直接任务创建、编辑、评论

## 11. 知识库

**核心的反目标。** 知识库不是 Paperclip 核心的一部分——它将是一个插件。任务系统 + 评论 + agent 描述提供了足够的共享上下文。

架构必须支持以后添加知识库插件（清晰的 API 边界、可挂接的生命周期事件），但核心系统明确不包含知识库。

---

## 12. 反需求

Paperclip 明确**不做的**事情：

- **不是 Agent 运行时**——Paperclip 进行编排，Agent 在其他地方运行
- **不是知识库**——核心没有 wiki/docs/vector-DB（插件领域）
- **不是 SaaS**——单租户、可自托管
- **对 Agent 实现不做意见**——任何语言、任何框架、任何运行时
- **不是自动自愈的**——显示问题，而不是静默修复
- **不管理交付基础设施**——没有仓库管理、没有部署、没有文件系统（但管理任务链接的文档和附件）
- **不自动重新分配工作**——过时任务会浮出水面，而不是静默重新分配
- **不跟踪外部收入/支出**——这是未来的插件。Token/LLM 成本预算是核心功能。

---

## 13. 原则（汇总）

1. **对如何运行您的 Agent不做意见。** 任何语言、任何框架、任何运行时。Paperclip 是控制平面，而不是执行平面。
2. **公司是组织单位。** 一切都在公司下。
3. **任务是沟通渠道。** 所有 Agent 通信都通过任务 + 评论流转。没有侧渠道。
4. **所有工作都追溯到目标。** 层级任务管理——没有什么是孤立存在的。
5. **董事会治理。** 人类通过董事会保持控制。保守默认（需要人类批准）。
6. **暴露问题，不要隐藏它们。** 良好的审计和可见性。没有静默自动恢复。
7. **原子所有权。** 每个任务单一 assignee。原子检出防止冲突。
8. **渐进式部署。** 本地启动很简单，扩展到托管也很直接。
9. **可扩展的核心。** 清晰的边界，因此插件可以添加功能（Adapter、知识库、收入跟踪）而无需修改核心。
